Technical brief

How tenantbleed proves tenant isolation in Supabase apps

A Supabase app's access control lives in Postgres row level security, functions and storage policies, called straight from the browser. tenantbleed tests that layer the way an attacker would: with real accounts, through the same APIs, on a throwaway copy of your app. A finding exists only when an attack worked.

What happens in a scan

  1. Build a copy. A local Supabase stack from your repository's migrations, in CI or on a laptop.
  2. Read the schema. Tables, policies, grants, functions, buckets, and who owns each row.
  3. Create two tenants. Two real test users, each with their own data, plus an anonymous visitor.
  4. Attack. Each actor tries to reach the other's data through the REST API, functions and storage.
  5. Confirm and clean up. Every hit is confirmed in the database, then everything the scan changed is undone.

What it covers

  • Every way in: tables, views, functions and storage buckets, through the same APIs your app's browser uses.
  • Every kind of harm: reading, changing, deleting or adding to another customer's data, and acting in another user's name.
  • Every kind of attacker: another signed-in customer, and anyone on the internet without an account.

Proven means confirmed. A finding counts only when the database shows the attack worked. A response code is never enough on its own.

Data that is public by design, such as a product catalog or public profiles, is recognised and reported lower, with the reason.

What you get

  • Results in the terminal and in a local web UI (loopback 127.0.0.1 only).
  • A plain sentence per issue: "Any logged-in user can delete other users' invoices."
  • The exact request, the proof, and a curl that reproduces it on your local stack.
  • A fix description and a prompt for Lovable, Bolt, Cursor or Claude.
  • Coverage: every table it could not test, with the reason. Never "clean" when coverage is incomplete.

Deterministic by design

No AI decides what is a finding. The same schema gives the same result on every run, so a finding can be reproduced, argued with and closed.

Tested fixes (preview)

Fixes come from fixed templates, not AI: enable RLS with owner policies, an owner-scoped restrictive policy, a backend-only policy limited to service_role, security_invoker views, functions run as the caller, one folder per owner in storage.

Each fix is applied to a fresh copy of the database. The attacks are re-run, then the owner, a workspace member and an admin must keep all the access they had. Otherwise the fix is rejected.

The access check earns its place: a naive "turn RLS on" fix stops every attack and also locks owners out of their own rows. The verifier rejects it.

Run it locally

# in your project, with the local stack up
supabase start

# headless: scan and gate on the exit code
npx tenantbleed supabase --fail-on high

# or open the local web UI
npx tenantbleed ui

Everything runs on your machine, nothing is sent off the box. The same command gates any CI on its exit code. Optional tenantbleed.json marks tables that are shared by design or a single-workspace app.

Safety and limits

  • Runs only on local, CI or disposable preview stacks and refuses other URLs. It creates users and writes data, so never production.
  • Supabase today: Postgres RLS, functions, views and storage. Edge functions and Realtime are not tested yet.
  • Apps that keep the tenant in a JWT claim rather than in foreign keys are only partly understood.
  • "Tested, not exploitable" means no attack worked with the test data. It is strong evidence, not a proof of safety.
